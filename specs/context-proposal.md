### DECISIÓN-1: Lenguaje, framework, y la interfaz unificada de búsqueda + ejecución local del Client Node
- Contexto: El sistema ya tiene un prototipo funcional en `google_maps_scraper.py` (Python + asyncio + Playwright). El Control Plane requiere FastAPI (dado explícitamente por ti). Restricción técnica insalvable: una pestaña de navegador NO puede lanzar ni controlar un Playwright/Chromium local — es una limitación de seguridad del navegador (sandboxing), independiente de qué framework se use para la Web App. Por eso el formulario de búsqueda (config, categoría, zona, botón "Buscar") no puede vivir solo en una Web App de navegador separada si quieres que la ejecución local ocurra sin que el usuario tenga que acordarse de tener "otra app" abierta: para un usuario no técnico de un solo negocio en una sola computadora, la forma más simple es que el Client Node sea a la vez la interfaz de creación de búsqueda Y el ejecutor local — un solo ícono, una sola ventana: doble clic, ve el formulario (config, categoría, zona, botón Buscar, resultados históricos) y el toggle "Ver navegador" (`headless`), da clic en Buscar, y esa misma app ejecuta el scraper localmente cuando el Backend le asigna el Job.
- Flujo resultante: (1) el usuario llena categoría/zona/config en la ventana del Client Node → (2) esa misma app llama `POST /searches` al Backend → (3) el Backend (Job Generator) expande zonas/categorías en Jobs y los encola → (4) el Backend empuja el Job por el WebSocket que esa misma app ya mantiene abierto (es el mismo canal de DECISIÓN-4/9/10, no una conexión aparte) → (5) el propio Client Node ejecuta el scraper Playwright localmente → (6) progreso/resultados suben por el mismo canal y se muestran en la misma ventana. Ninguna terminal, ninguna segunda app que el usuario deba recordar mantener abierta.
- Opciones:
  - A. **Flet (Python sobre Flutter)** para la ventana completa (formulario de búsqueda + config + resultados) que arranca y gestiona el motor Python + asyncio + Playwright ya existente **en el mismo lenguaje, sin sidecar ni IPC entre procesos de distinto runtime**; empaquetado con `flet build` por SO. El mismo código Flet puede correr también en modo web (sin reescribir la UI) el día que quieras una vía secundaria por navegador.
  - B. PySide6 (Qt for Python) — igual 100% Python, más maduro y probado en producción que Flet, pero no tiene una vía nativa para convertirse en app web sin reescribir la UI, y requiere más esfuerzo de diseño para verse moderna.
  - C. Tauri o Electron + sidecar Python (lo que veníamos evaluando) — da el shell más pulido y el mejor auto-actualizador ya construido, pero agrega un lenguaje/ecosistema nuevo completo (Rust+JS, o solo JS) a un equipo que hasta ahora ha construido TODO este sistema en Python (Backend, agente LLM, scraper) — dos toolchains de build que mantener para siempre, un protocolo de IPC entre shell y sidecar, y una comunidad distinta a la que recurrir cuando algo falle.
- Recomendación: honestidad primero — mi inclinación anterior por Tauri fue en parte porque tú lo mencionaste, y el beneficio que usé para venderlo (auto-actualización silenciosa) no lo pediste explícitamente, lo agregué yo. Al reevaluar sin anclarme a eso: para un equipo 100% Python en todo lo demás, meter Rust/JS solo por la ventana del Client Node es un costo de mantenimiento permanente, no solo de arranque. Recomiendo Opción A (Flet): mismo lenguaje que el resto del sistema, arranca Playwright sin IPC entre lenguajes, y el mismo código sirve después como app web sin reescribir — resuelve el flujo completo (formulario → API → Job → cola → WebSocket → ejecución local → resultados en la misma ventana) igual que Tauri, con una pieza menos. Riesgo a mitigar: nunca hemos validado que `flet build` empaquete bien Playwright+Chromium en los tres SO — propongo una prueba de concepto de un día en Fase 0 (ventana mínima que arranca Playwright) antes de comprometernos del todo; si falla, B (PySide6) es la caída segura, sigue siendo 100% Python.
- Consecuencias: `apps/client-node` es un solo paquete Python (sin split shell/worker de lenguajes distintos) — un solo CI, un solo lenguaje, un solo equipo de habilidades. La auto-actualización no viene gratis como en Tauri: v1 puede lanzar con un chequeo simple ("hay una versión nueva, descárgala") y una auto-actualización silenciosa se construye como iteración posterior solo si la validas como necesaria. Firma de código en Windows + notarización en macOS y compilación por SO en CI se mantienen igual que en cualquier app de escritorio nativa — eso no depende del framework elegido.

### DECISIÓN-2: Base de datos y ORM
- Contexto: Ya decidiste PostgreSQL con estrategia multi-tenant de datos independientes. Falta la capa de acceso a datos.
- Opciones:
  - A. SQLAlchemy 2.0 (async) + Alembic — el más maduro en Python, soporta RLS de Postgres sin fricción, migraciones versionadas.
  - B. SQLModel (Pydantic + SQLAlchemy) — más ergonómico (unifica modelos de API y DB), pero es una capa más joven con limitaciones documentadas en relaciones complejas.
  - C. Sin ORM, SQL crudo con asyncpg — máximo control, pero mapeo manual, más riesgo de errores de seguridad en parametrización, y choca con el estándar de "constraints en base de datos" salvo disciplina estricta.
- Recomendación: Opción A — SQLAlchemy 2.0 async + Alembic. Estándar de facto para FastAPI + Postgres, soporte probado para políticas RLS (necesario para DECISIÓN-5), y Alembic da migraciones versionadas (exigidas en Fase 2).
- Consecuencias: `specs/migrations/` se implementa como migraciones Alembic; los modelos de dominio se separan de los modelos SQLAlchemy para no acoplar dominio a infraestructura.

### DECISIÓN-3: Patrón de arquitectura, capas, estructura del repositorio y ubicación de los canales
- Contexto: El sistema combina piezas con ciclos de vida y confianza distintos: Control Plane (confiable), Client Node (worker, "entorno no confiable"), Scraper Engine (librería usada solo por el Client Node), canales de entrada (Telegram, con WhatsApp como canal futuro), y el Panel de administración (DECISIÓN-14, para ti como operador, no para el cliente final). Por DECISIÓN-1, la interfaz primaria de búsqueda del cliente final ya no es una Web App aparte: es la misma ventana Flet del Client Node. Una Web App de navegador para el cliente final pasa a ser un despliegue **secundario y opcional** de ese mismo código Flet, para quien quiera ver resultados sin tener el Client Node instalado — sin capacidad de ejecutar nada local. Telegram no es solo una interfaz suelta: es un canal de comunicación que necesita su propia lógica de validación de webhook y mapeo de identidad (telegram_user_id -> user_id), y más adelante un segundo canal (WhatsApp) con el mismo patrón. El principio "the client executes, the server decides" exige además una frontera dura entre Backend y Client Node.
- Opciones:
  - A. Monorepo con `apps/api` (FastAPI, Clean Architecture: domain -> application -> infrastructure -> api), `apps/client-node` (Flet, un solo paquete Python, DECISIÓN-1), `apps/admin-panel` (Flet web, DECISIÓN-14, un operador, mismo lenguaje que client-node), `apps/channels-service` (Telegram hoy, WhatsApp después, detrás de una interfaz `ChannelAdapter` que traduce el mensaje del canal a las mismas llamadas de la API pública) + `packages/shared-contracts`. La UI de `apps/client-node` puede desplegarse también, sin reescribirla, como sitio web independiente (`b2b-lead-generation-web`, repo aparte) el día que quieras esa vía secundaria de acceso para el cliente final.
  - B. Cuatro repos separados (control-plane, client-node, channels-service, web) — aislamiento total, pero cuatro pipelines de CI y cuatro releases coordinados desde el día uno para tres componentes que hoy comparten equipo y lenguaje (los tres primeros son Python).
  - C. Meter Telegram (y WhatsApp después) como un módulo dentro de `apps/api` en vez de un app aparte — menos piezas al inicio, pero mezcla el ciclo de vida de un canal de mensajería (reglas y rate limits propios de Telegram/WhatsApp, verificación de firma de webhook) con el del Control Plane, y dificulta escalar o desplegar el bot de forma independiente si el volumen de mensajes crece.
- Recomendación: Opción A. `channels-service` y `admin-panel` viven en este mismo repo (comparten lenguaje/CI con control-plane y client-node) pero cada uno se despliega independiente y **solo consume la API pública del Control Plane** — ninguno importa su código interno. Así: **este repo** = control-plane + client-node (Flet, un solo paquete Python) + admin-panel (Flet web) + channels-service (Telegram ahora, WhatsApp con el mismo adapter después) + shared-contracts. Una eventual Web App de solo lectura para el cliente final reutiliza el código del client-node sin reescribirlo, en un repo aparte solo cuando decidas construirla. No fusiono el canal dentro de control-plane (opción C) porque validar webhooks y mapear identidad de un canal de mensajería es una responsabilidad distinta (SOLID-S) del Control Plane, aunque convenga que viva en el mismo repositorio operativo.
  **Nota de alcance para Fase 2:** esta decisión fija el tipo de proyecto combinado según la tabla "Alcance del proceso": API/backend + Agente LLM (Job Generator) + Sistema multi-tenant + Worker/job (Client Node). Fase 2 debe producir `migrations/` + `openapi.yaml` + `graph.md`/`prompts/`/`tools.md`/`evals/` (para el Job Generator) + contrato de entrada/salida e idempotencia (para el Client Node).
- Consecuencias: `channels-service` mantiene su propia tabla `channel_identity` (`telegram_user_id`/`whatsapp_phone` -> `user_id`) sin lógica de negocio propia — solo traduce y llama a la API pública, mismo principio de "no business logic" que el Client Node; agregar WhatsApp después es un adapter nuevo dentro de `channels-service`, sin tocar Control Plane ni Client Node. `admin-panel` solo consume endpoints protegidos por el rol `admin` de DECISIÓN-4, nunca lógica interna del Control Plane. Todas las apps del repo son Python (control-plane, client-node, admin-panel, channels-service); CI corre pipelines separados por app; `packages/shared-contracts` es la única dependencia cruzada permitida entre apps de este repo.

### DECISIÓN-4: Autenticación y autorización
- Contexto: Tres actores con necesidades distintas: usuarios de Web App, usuarios de Telegram (ya identificados por su Telegram user ID), y Client Nodes no confiables que reciben Jobs por WebSocket. Ya diste "Token authentication" y "Rotating tokens" para el Client Node.
- Opciones:
  - A. JWT (access + refresh con rotación) para Web App; vínculo Telegram↔cuenta vía token de enlace de un solo uso; Client Node se autentica con las mismas credenciales de la cuenta del usuario final (el dueño del negocio inicia sesión dentro de la ventana del Client Node, no es un dispositivo pre-registrado por un admin) y recibe un token de corta duración, rotado en cada reconexión WebSocket.
  - B. Sesiones de servidor (cookies) + API keys estáticas de larga duración para Client Node — contradice "rotating tokens" y las cookies no aplican bien a un proceso headless por WebSocket.
  - C. OAuth2 delegado (Auth0/Clerk) para Web App + JWT propio para Client Node — evita construir auth de usuarios, pero introduce una dependencia de pago de terceros no solicitada.
- Recomendación: Opción A. Es la única que cumple "rotating tokens" tal como lo especificaste. RBAC simple (admin/user por cuenta); el Client Node no tiene rol de negocio propio, solo hereda el `user_id` de quien inició sesión, con un scope técnico (worker) sin acceso a endpoints administrativos.
- Consecuencias: tabla `client_tokens` con expiración corta (ej. 1h) y mensaje WebSocket de rotación; comprometer un Client Node expone como máximo esa ventana y los datos de ese usuario, nunca los de otro.

### DECISIÓN-5: Mecanismo de aislamiento multi-tenant
- Contexto: Exigiste "datos independientes, sin mezclar datos de cada usuario" sobre PostgreSQL. Ajuste tuyo: el campo de aislamiento es `user_id` (la cuenta de login), no un `tenant_id` separado — cada usuario es su propio silo de datos.
- Opciones:
  - A. Esquema compartido + `user_id` en cada tabla + Row-Level Security (RLS) de Postgres — aislamiento forzado por el motor de base de datos, escalable a muchos usuarios sin explosión de migraciones.
  - B. Un esquema por usuario — aislamiento lógico visible, pero cada usuario nuevo exige correr migraciones contra un esquema nuevo (caro operacionalmente a partir de decenas de usuarios).
  - C. Una base de datos por usuario — aislamiento máximo, pero sobre-ingeniería costosa para un B2B con muchos usuarios pequeños desde el día uno.
- Recomendación: Opción A. Es el mecanismo que ASDP-PROCESS.md ya asume (Fase 0 verifica "rol NO-superusuario y sin BYPASSRLS"), y escala mejor que esquema-por-usuario. El aislamiento lo garantiza Postgres, no la disciplina del desarrollador en cada query.
- Consecuencias: cada tabla nueva en Fase 2 incluye `user_id NOT NULL` + política RLS en la misma migración; el rol de aplicación se conecta sin BYPASSRLS; todo Job y JobResult llevan `user_id` de origen y el Client Node nunca ve datos de más de un usuario por Job. Nota para el futuro (no bloquea esta decisión): con `user_id` como límite de aislamiento, cada cuenta de login es su propio silo — si más adelante necesitas que varios usuarios humanos (ej. empleados de una misma empresa) compartan el mismo conjunto de datos/suscripción, vas a necesitar una entidad "Organización" por encima de `user_id`. Lo dejo documentado para que no sea sorpresa después.

### DECISIÓN-6: Stack de testing, linter y package manager
- Contexto: monorepo Python con dos paquetes (backend async + worker con Playwright).
- Opciones:
  - A. pytest + pytest-asyncio + httpx (test client FastAPI) + pytest-playwright (Client Node) + ruff (lint+format) + uv (package manager con soporte de workspaces).
  - B. unittest (stdlib) + flake8 + pip-tools — cero dependencias nuevas, pero más verboso para fixtures async y más piezas sueltas (flake8 no formatea).
  - C. pytest + tox + poetry — poetry resuelve dependencias más lento que uv; tox añade complejidad no necesaria para un monorepo de dos paquetes con CI simple.
- Recomendación: Opción A. ruff reemplaza flake8+black+isort en una sola herramienta; uv es el gestor más rápido del ecosistema actual y soporta workspaces de monorepo (necesario por DECISIÓN-3); pytest-asyncio cubre el código async; pytest-playwright da fixtures de browser para el Scraper Engine.
- Consecuencias: `uv.lock` en la raíz con workspace members control-plane/client-node; `ruff.toml` único para todo el monorepo; cobertura con pytest-cov.

### DECISIÓN-7: Contratos de error del proyecto
- Contexto: múltiples canales de error (REST para Web App, WebSocket para Client Node, conversacional para Telegram). Regla de seguridad: mensajes genéricos al cliente, detalle interno solo al logger.
- Opciones:
  - A. `DomainError` base con subclases específicas (`ValidationError`, `UserIsolationError`, `JobExecutionError`, `PaymentError`...), envelope único `{"error": {"code", "message", "details"}}` en REST, y un tipo de mensaje `error` versionado con el mismo `code` en el protocolo WebSocket.
  - B. `HTTPException` nativas de FastAPI sin capa de dominio — menos código al inicio, pero mezcla excepciones de infraestructura en la lógica de negocio, violando la capa de dominio de DECISIÓN-3.
  - C. Siempre 200 con `success: false` — rompe convenciones REST que `openapi.yaml` y cualquier cliente HTTP esperan.
- Recomendación: Opción A. Consistente con la capa de dominio ya elegida y con la regla de mensajes genéricos: `code` estable y mapeable, `message` genérico, detalles internos solo al logger.
- Consecuencias: cada endpoint de `openapi.yaml` documenta sus `DomainError` posibles como respuestas tipadas; el protocolo WebSocket define su propio catálogo de error codes (`JOB_TIMEOUT`, `BROWSER_CRASH`, `RATE_LIMITED_BY_TARGET`, ...).

### DECISIÓN-8: LLM del Job Generator — proveedor, reintentos, presupuesto de tokens
- Contexto: El Job Generator interpreta instrucciones en lenguaje natural (ej. "academias de belleza 5 estrellas en todo Nuevo León"), debe expandir la zona a municipios, separar categorías, aplicar la configuración del usuario (`segmentation`, `search`) y generar un Job estructurado por combinación zona×categoría. Quieres poder elegir el proveedor/modelo (Claude, GPT, Gemini, Groq/Llama, u otro) sin tocar código — ya tienes un patrón funcionando en otro proyecto tuyo (`agent_graph.py`) basado en LangChain con un if/elif por proveedor.
- Opciones:
  - A. LangChain como capa de abstracción multi-proveedor, usando `init_chat_model(model, model_provider=...)` (el inicializador universal de LangChain — una sola llamada resuelve el proveedor) en vez de importar y ramificar a mano por proveedor. La selección de proveedor+modelo (ej. `"groq"` + `"llama-3.3-70b-versatile"`) se guarda en una tabla `ai_provider_config` en Postgres — así se cambia sin redeploy — y las API keys de cada proveedor (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GROQ_API_KEY`, `GOOGLE_API_KEY`) viven SOLO en variables de entorno, nunca en la base de datos ni en código, por la regla absoluta de seguridad de CLAUDE.md.
  - B. Un `LLMProvider` propio (protocolo/interfaz) con un adaptador escrito a mano por proveedor usando el SDK oficial de cada uno (`anthropic`, `openai`, `google-genai`, `groq`) sin LangChain — más control fino sobre features específicas de cada proveedor, cero riesgo de que una actualización de LangChain rompa el comportamiento, pero más código propio que mantener por cada proveedor nuevo.
- Recomendación: Opción A. Ya tienes esta ruta validada en producción en otro proyecto tuyo — no hay razón para descartar algo que ya funciona. La mejora sobre tu snippet: (1) `init_chat_model` en vez de if/elif — LangChain resuelve el proveedor por ti, una línea menos que mantener por cada proveedor nuevo; (2) la selección de proveedor/modelo se mueve de una constante `LLM_MODEL` fija en código a una tabla de configuración en base de datos, para poder cambiar de Gemini a Groq (como ya te pasó) sin redeploy; (3) las API keys se quedan exclusivamente en `.env` — la tabla de configuración solo guarda el nombre del proveedor y del modelo, dato no sensible. La tool `generar_jobs` (JSON Schema estricto: zona expandida, categoría, parámetros heredados de la configuración del usuario) es la misma sin importar el proveedor activo. Reintentos: 3 con backoff exponencial envueltos en el factory (vía `.with_retry()` de LangChain), iguales para cualquier proveedor; si los 3 fallan, el Job se encola para revisión humana — nunca se ejecuta con una salida no validada. Presupuesto: ~2000 tokens de salida por instrucción típica, aplicado como límite de la tool/schema, independiente del proveedor.
- Consecuencias: agregar un proveedor nuevo es una fila nueva en `ai_provider_config` + su paquete de LangChain (`langchain-anthropic`, `langchain-openai`, `langchain-google-genai`, `langchain-groq`, ...) instalado, sin tocar el resto del Job Generator; requiere un catálogo verificado de municipios/zonas por estado disponible como contexto/tool, para que el modelo no invente municipios inexistentes; el schema estricto de Job es el contrato entre Fase 2 (`graph.md`/`tools.md`) y la implementación, independiente del proveedor elegido.

### DECISIÓN-9: Cola y scheduler (cron + queues)
- Contexto: el Backend "nunca ejecuta scrapers" pero sí planifica y encola Jobs para que los Client Nodes los tomen vía WebSocket, con soporte de tareas programadas además de bajo demanda.
- Opciones:
  - A. Redis + `arq` (cola async nativa para asyncio) + cron nativo de arq — encaja de forma natural con FastAPI async, una sola dependencia de infraestructura nueva.
  - B. Celery + Redis/RabbitMQ — el más maduro, pero es sincrónico por diseño (workers de hilos/procesos) y encaja peor con un Control Plane 100% async; trae más configuración de la necesaria.
  - C. PostgreSQL como cola (`SELECT FOR UPDATE SKIP LOCKED`) — cero infraestructura nueva, pero un Job aquí no se "ejecuta" en el Backend, solo se asigna a un Client Node conectado por WebSocket; se pierde la ventaja de pub/sub en tiempo real y habría que construirla a mano.
- Recomendación: Opción A. `arq` + Redis está diseñado para asyncio (mismo runtime que FastAPI y WebSockets), soporta cron nativamente, y Redis sirve además como backend de pub/sub para notificar a los Client Nodes conectados cuándo hay un Job disponible.
- Consecuencias: Redis se suma como dependencia de infraestructura (entra en el docker-compose de Fase 0); el Scheduler solo encola — la asignación real ocurre en la capa WebSocket.

### DECISIÓN-10: Protocolo del canal WebSocket Backend↔Client Node
- Contexto: "Send job" y "Results + logs sender" son el único canal de control entre el Backend y un Client Node no confiable. Necesita mensajes tipados y versionados.
- Opciones:
  - A. Mensajes JSON con envelope `{"type", "version", "payload"}`, validados con los mismos modelos Pydantic del contrato compartido (`packages/shared-contracts`) en ambos lados.
  - B. JSON libre sin schema formal, validado ad-hoc — más rápido de prototipar, pero cualquier cambio de forma rompe silenciosamente al otro lado.
  - C. Protocolo binario (protobuf/MessagePack) — más eficiente en bytes, pero agrega una etapa de build que no se justifica para el volumen de mensajes de control de este sistema.
- Recomendación: Opción A. Mismo principio que DECISIÓN-7 aplicado al canal WebSocket; `packages/shared-contracts` es la fuente única de verdad para el shape de cada mensaje.
- Consecuencias: `specs/design.md` de la iteración correspondiente documenta la tabla de tipos de mensaje (`job.assign`, `job.result`, `job.log`, `client.register`, `client.token_rotate`, `error`) igual que documentaría endpoints REST. Política de despacho (DECISIÓN-11): el Backend manda `job.assign` de uno en uno por Client Node conectado — espera el `job.result` correspondiente antes de mandar el siguiente. Es el único control de concurrencia del sistema; el Client Node no implementa ningún límite propio.

### DECISIÓN-11: Límite de confianza y alcance del Client Node
- Contexto: El empaquetado ya quedó resuelto en DECISIÓN-1 (Flet, un solo paquete Python, instalador nativo por SO vía `flet build`). Esta decisión es sobre qué puede y qué NO puede tener/hacer el Client Node, dado que corre en una máquina fuera del control del operador ("Untrusted client environment", "No business logic", "No secrets exposed"). Confirmaste: el Client Node es "tonto" — el usuario final solo inicia sesión con su cuenta (`user_id`), recibe Jobs ya resueltos por el Backend, los ejecuta, y envía resultados/logs. No contiene clave de ningún LLM, no contiene credenciales de proveedor de pago, no tiene acceso a datos de otro usuario.
- Opciones:
  - A. El Client Node solo guarda en disco, cifrado localmente, el token de sesión rotativo (nunca una API key de negocio); todo lo demás (parámetros de búsqueda, catálogo de municipios, decisión de cuántos Jobs le tocan) llega desde el Backend en cada asignación de Job — el cliente no decide nada, solo ejecuta y reporta.
  - B. El Client Node cachea localmente configuración de negocio (ej. límites del plan, catálogo de zonas) para funcionar offline por más tiempo — reduce llamadas al Backend, pero mueve una fuente de verdad de negocio a una máquina que el operador no controla, y ese caché podría quedar desactualizado o ser manipulado sin que el Backend lo note de inmediato.
- Recomendación: Opción A. Es la aplicación literal de "the client executes, the server decides": ni el límite de uso, ni el catálogo de zonas, ni la validez de un resultado se deciden en el Client Node — solo se ejecutan ahí. Esto es lo mismo que ya definiste, solo lo dejo explícito como regla de diseño para que Fase 2 y Fase 5 no le agreguen "inteligencia" al cliente por conveniencia.
- Consecuencias: el instalador no incluye clave de ningún LLM, ni de proveedor de pago, ni credenciales de otro usuario — solo el token de sesión rotativo de DECISIÓN-4; el Backend nunca asigna más Jobs de los que le tocan al usuario según su plan (el límite existe únicamente ahí, no como un contador que el cliente deba respetar por sí mismo); comprometer el binario del Client Node en la máquina de un usuario expone como máximo la sesión de ESE usuario, nunca datos ni presupuesto de otro. **"Usage limiter" (eliminado, decisión explícita):** no existe ningún límite de concurrencia propio del Client Node. El Backend despacha los Jobs de una búsqueda **de uno en uno** por el WebSocket — manda `job.assign`, espera el `job.result` correspondiente, y hasta entonces manda el siguiente. Ese ritmo de entrega ES el único control de concurrencia del sistema; el Client Node no decide cuántos ejecutar a la vez, solo ejecuta el que le llega. Esto se documenta como parte del protocolo WebSocket de DECISIÓN-10, no como lógica nueva del Client Node.

### DECISIÓN-12: Anti-detección del Scraper Engine
- Contexto: "Behavior rotation, Random delays, Variable navigation, Unique fingerprint per client" ya están en tu descripción como requisitos. Hay dos tipos de parámetro distintos aquí: (1) el **fingerprint** (user-agent, viewport, locale, timezone) debe ser estable por instalación a través del tiempo — un navegador real no cambia de identidad entre visitas; (2) **behavior rotation / delays / navegación variable** es aleatoriedad que debe variar en cada ejecución, no persistirse. Señalaste correctamente el riesgo de generar el fingerprint dentro del mismo binario que se distribuye a todos: la diversidad real depende de qué tan rico sea ese generador embebido, y con un pool limitado hardcodeado es fácil que muchas instalaciones terminen con combinaciones repetidas — lo contrario de lo buscado. Además, decidir la estrategia anti-detección es una decisión, y "the client executes, the server decides" dice que le toca al servidor, no al cliente.
- Opciones:
  - A. Playwright + `playwright-stealth` con el **Backend generando y asignando el fingerprint** por instalación (un `device_id` único generado en el primer arranque del Client Node, no por `user_id` — así el mismo usuario con dos computadoras obtiene dos fingerprints distintos, nunca el mismo dos veces). El Backend mantiene un pool curado de combinaciones UA/viewport/locale/timezone realistas con garantía de unicidad, lo asigna en el mensaje `client.register` de DECISIÓN-10, y el Client Node lo cachea localmente para reutilizarlo en cada sesión (estable, pero decidido y auditable centralmente). Las rangos de comportamiento (delays, patrones de scroll, variantes de navegación) también los define el Backend como una "política" versionada que el cliente sortea localmente en cada ejecución — la política es centralizada, el sorteo real es local y distinto en cada Job.
  - B. Todo generado y persistido localmente por el Client Node (mi recomendación original) — más simple de implementar, pero como señalaste, la diversidad del pool queda fija en el código que se distribuye a todos, sin visibilidad ni control del operador, y no se puede mejorar la estrategia sin publicar una nueva versión del cliente.
  - C. Playwright + servicio de navegador administrado de terceros (ej. Browserless, Bright Data) — delega el anti-detección a un proveedor, pero contradice "Local execution"/"Local Client" ya decidido.
- Recomendación: Opción A. Corrige el punto que señalaste: con el Backend como fuente de la verdad del pool de fingerprints y de las políticas de comportamiento, puedes garantizar unicidad real entre instalaciones, ampliar o corregir el pool cuando detectes que algo empieza a fallar (ej. Google Maps bloqueando un patrón específico) sin depender de que cada usuario reinstale el Client Node, y mantener trazabilidad de qué fingerprint usó cada instalación. El comportamiento aleatorio por ejecución (delays, scroll) se queda como sorteo local dentro de los rangos que manda el Backend — no tiene sentido que el servidor decida el milisegundo exacto de cada espera, solo el rango.
- Consecuencias: nueva tabla `device_fingerprints` (`device_id`, `user_id`, perfil asignado, fecha de asignación) en el Control Plane, con constraint de unicidad sobre el pool activo; el mensaje `client.register` de DECISIÓN-10 ahora también devuelve el fingerprint asignado y la versión vigente de la política de comportamiento; el Client Node nunca decide su propio fingerprint, solo lo cachea y lo aplica — consistente con DECISIÓN-11 (el cliente ejecuta, no decide); `specs/design.md` de la iteración correspondiente define el schema del pool y el algoritmo de asignación sin repetición.

### DECISIÓN-13: Proveedor de pagos
- Contexto: "Payment validation" y "Payment automation" son requisitos del Control Plane. Tú confirmaste que el proveedor real aún no está decidido y pediste un adapter/mock.
- Decisión (ya definida por ti, documentada como ADL): usar el patrón adapter — sin proveedor real todavía.
- Recomendación de implementación: interfaz `PaymentProvider` en la capa de aplicación (puerto, DIP), con un `MockPaymentProvider` en infraestructura para desarrollo/tests, y un contrato de eventos de pago (`payment.validated`, `payment.failed`, `subscription.renewed`) desacoplado del proveedor concreto. Cuando definas el proveedor real (Stripe/Mercado Pago/Conekta/otro), se implementa un adaptador nuevo sin tocar dominio ni aplicación.
- Consecuencias: ningún flujo de negocio (activar cuenta, limitar uso) depende del SDK de un proveedor específico; la iteración que integre el proveedor real deberá definir en su propio `openapi.yaml` el contrato de webhooks; el mock debe simular success/failure de forma determinística para tests.

### DECISIÓN-14: Panel de administración
- Contexto: Como operador del sistema necesitas ver cuántos usuarios tienes, las búsquedas de cada usuario, cuántos leads ha generado cada usuario, y ejecutar operaciones administrativas (activar/desactivar cuenta, ver estado de pago, ajustar límites). Esto es distinto de cualquier interfaz de cliente final (DECISIÓN-1/3) — es tu propia herramienta operativa, y sí necesita estar alojada en un dominio, accesible solo con el rol `admin` de DECISIÓN-4. No estaba cubierto explícitamente en las decisiones anteriores; lo agrego aquí porque tu pregunta lo dejó en evidencia.
- Opciones:
  - A. SQLAdmin/Starlette-Admin montado sobre `apps/api` — descartada por tu preferencia de un panel construido a medida, no un scaffold auto-generado.
  - B1. Panel custom construido en **Flet web** (Python) — mismo framework y lenguaje que ya usa `apps/client-node` (DECISIÓN-1), corre como app web propia (no de escritorio) en `apps/admin-panel`, con control total de diseño/gráficas. El equipo no agrega ningún lenguaje nuevo: sigue siendo 100% Python en todo el sistema.
  - B2. Panel custom en React (u otro framework JS/SPA) — ecosistema más maduro específicamente para dashboards administrativos (tablas, filtros, gráficas ricas), pero reintroduce un lenguaje/stack nuevo (JS) solo para esta herramienta interna de un solo operador — justo el costo que evitamos en DECISIÓN-1 al descartar Tauri/Electron para el Client Node.
  - C. Dashboard de BI externo (ej. Metabase/Retool) de solo lectura — rápido de montar, pero no permite ejecutar acciones administrativas (activar cuenta, resetear límite), solo ver datos, y es una herramienta de terceros más que operar.
- Recomendación: **Opción B1 (Flet web), confirmada por ti explícitamente** — pese a que conoces React/JS mejor que Python, prefieres mantener un solo lenguaje en todo el sistema. Es una elección válida: un panel construido a tu medida (no un scaffold genérico) sin abrir un segundo frente tecnológico, mismo framework y lenguaje que ya mantiene el Client Node.
- Consecuencias: sí existe algo alojado en un dominio desde el día uno — este panel; requiere que el rol `admin` de DECISIÓN-4 controle el acceso (nunca el mismo login que un cliente final); es una app completa que se construye y mantiene con el mismo esfuerzo de cualquier frontend propio, más que un scaffold gratis como SQLAdmin. `apps/admin-panel` (Flet web) ya quedó reflejado en DECISIÓN-3.
